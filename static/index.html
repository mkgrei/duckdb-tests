DuckDB, explained

Why does it exist, what makes it different, and why is everyone in data suddenly using it? Scroll through the ideas, then try them live in the playground.

1Why does DuckDB exist?

Databases historically split along two axes. The workload axis: OLTP systems (online transaction processing) handle many tiny reads and writes — "update this order", "fetch this user" — while OLAP systems (online analytical processing) answer big questions over lots of rows — "revenue per region per month". The deployment axis: a client–server database runs as its own process you connect to over a socket, while an in-process database is just a library living inside your application.

Fill in the grid and you find three crowded corners… and one that was empty for decades:

SQLite for analytics. That's the elevator pitch. Analysts and data scientists were stuck choosing between heavyweight warehouses (Snowflake, BigQuery — powerful, but remote, slow to set up, costly) and in-memory dataframes (pandas — convenient, but no SQL engine, single-threaded, dies on larger-than-RAM data). DuckDB (born 2019 at CWI, the Dutch research institute behind decades of database research) filled the gap: a full analytical SQL engine you just pip install.

2Columnar storage: read only what you need

A row store lays each row's values contiguously — perfect for "fetch order #42 with all its fields". A column store lays each column's values contiguously — perfect for "average price across a million orders", because the engine reads only the price column and skips the rest.

On real tables with dozens of columns and millions of rows, this gap is the difference between seconds and minutes. Columnar layout also compresses far better, since values of the same type sit next to each other.

3In-process: a database as a library

There is no DuckDB server. No port, no credentials, no daemon to babysit. import duckdb and the entire engine lives inside your process — a query is a function call, and results land in your program's memory with zero copies over a network.

Why it matters: the red dot pays for serialization, sockets and round-trips on every batch of rows. The green dot is a C++ function call. When a query produces a big result — typical in analytics — transfer cost can dominate everything else. It also means setup is pip install duckdb, and your "database" is a single file you can email to a colleague.

4Vectorized execution: process 2048 rows at a time

Storage is only half the story — execution style is the other half. Classic engines interpret query plans one tuple at a time: every row is pushed through every operator with function calls, branches, and virtual dispatch. DuckDB processes vectors of ~2048 values per call: the per-call overhead is amortized 2048×, the inner loops are tight and branch-free, and data stays hot in the CPU cache.

5The superpowers you'll actually feel

Query files directly — no import step. A file path is a table:

SELECT category, avg(price)
FROM 'products.parquet'          -- yes, that's the FROM clause
JOIN 'sales.csv' USING (product_id)
GROUP BY category;

CSV, Parquet, JSON, even files over HTTP or on S3 — DuckDB reads them in place, infers schemas, and pushes column/filter selections down into the file scan.

Larger-than-RAM processing. Queries spill gracefully to disk, so "my laptop has 16 GB" no longer means "my dataset must fit in 16 GB".

Full modern SQL. Window functions, CTEs, PIVOT, list/struct types, plus ergonomic extras like GROUP BY ALL and SELECT * EXCLUDE (…).

Plays well with the ecosystem. Zero-copy exchange with pandas, Polars and Arrow; a single-file database format; extensions for Postgres, SQLite, JSON, geospatial…
